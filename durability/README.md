# LaminaDB 耐久性对照：在线提交与备份还原的确认边界

本文记录一次针对 LaminaDB 的耐久性核验。核验对象不是"最终查询是否一样"，而是
**三种确认结果与它们各自的实际效果是否配对**：

| 观测类别 | 含义 |
| --- | --- |
| `2xx` | 服务端在应答前已发布耐久结果 |
| `error` | 服务端返回领域错误（未发布，或明确表示存储结果不确定） |
| `no_response` | 传输失败或应答未被读到；调用方无法知道提交是否落盘 |

**核心结论：最终查询相同，不构成交付等价。** 本实验构造出两个反例：一个 `error`
应答后又"活过来"的提交，以及一份行完全一致但变更历史不同的还原副本。

`bin/laminad` 是 **Mach-O arm64** 产物（`go1.27.0` 构建），在本 Linux 环境无法执行
（`Exec format error`）。因此**所有证据都来自从同一提交重新构建的 Linux 二进制**，
上表哈希即该构建。没有修改任何产品代码；`go vet ./...` 通过。

Dockerfile 使用 `golang:1.25-bookworm`，与本机 1.25.0 一致。镜像层数、`-trimpath`
均未改动。

### 1.2 复现命令

```sh
sh durability/scripts/build.sh /tmp/canonical        # 需要 go 与 gcc
cd durability/harness
python3 -I experiments.py \
    --binary /tmp/canonical/laminad \
    --injector /tmp/canonical/fsync_inject \
    --out ../evidence --repeat 15 --workroot /dev/shm
```

单轮 8 个场景合计约 1.7 秒；15 轮重复约 25 秒。占用空间在 tmpfs 上，单轮峰值
远小于 100 MiB（每个提交帧最大约 15 MB，单场景最多两次）。

## 2. 环境限制（先说清楚，否则下面的结论会被过度解读）

本构建环境**没有任何容器运行时**，这是硬限制，不是省略：

```
docker CLI        absent
podman CLI        absent
docker.sock       absent
/run/containerd   absent
unshare -Ur       "Operation not permitted"
CapEff            0000000000000000   (无 CAP_SYS_ADMIN)
/dev/fuse         absent
```

`192.168.65.2:2375/2376` 接受 TCP 连接但永不回应 HTTP，不是可用的 daemon。
因此：

- **原生环境**：已完成实测，证据见 `evidence/canonical-native.json`。
- **容器环境**：**未测量**。协议已预注册在 `container/container_arm.py`（可用
  `--print-protocol` 查看）。该脚本在没有运行时的情况下拒绝对容器列作任何断言，
  `evidence/canonical-container.json` 的 `status` 为 `not_executed`。

> 容器列是 **未测量**，不是"与原生相等"。把这两者混为一谈正是本文要防止的错误。

另外两个限制影响结论强度，逐一登记：

1. **无法丢弃页缓存**（`/proc/sys/vm/drop_caches` 只读）。因此 `SIGKILL` 只能证明
   "进程内已发布的记录在重启后仍在"，**不能**证明"已 fsync 的字节在掉电后仍在"。
   `S3` 正是利用这一点构造反例，而不是假装没有这个缺口。
2. **无法在块设备层制造 I/O 错误**。故障控制改用两个真实路径：
   `prlimit --fsize`（真实 `EFBIG`）与 ptrace 写 `NT_ARM_SYSTEM_CALL`（使目标
   `fsync` 返回真实 `ENOSYS`）。二者都让内核返回真实错误，不是打补丁或改产品代码。

### 2.1 证据强度与成本（按题目要求显式选择）

| 方案 | 强度 | 成本 | 真实性 | 选择 |
| --- | --- | --- | --- | --- |
| 按时间窗 `SIGKILL` | 弱：窗口随负载漂移，无法区分"未落盘"与"已落页缓存" | 低 | 高 | 仅用 S0 做基线 |
| `prlimit --fsize`（`EFBIG`） | 强：内核真实拒绝写入，确定性 | 低 | 高（真实写路径） | **采用（S4）** |
| ptrace 改写 `fsync` 返回 `ENOSYS` | 强：真实进入产品错误分支，确定性可自检 | 中：需自建工具并验证 | 中：故障是外部的，但错误路径是真的 | **采用（S3）** |
| 块设备 `/dev/mapper` error target、`dm-flakey` | 最强（可真正丢字节） | 高：需 root/容器+内核模块 | 高 | **不可用**（无权限） |
| 页缓存丢弃 + `SIGKILL` | 强，但只覆盖掉电语义 | 中 | 高 | **不可用**（只读） |

选择理由：在"时间/空间有限 + 无法获得 root"的约束下，`prlimit` 与 ptrace 是能在
**不修改产品、不伪造结果**的前提下获得确定性错误路径的上限。它们能证明产品如何
*应答*失败，但不能证明介质真的丢了字节——这个界限在第 6 节明确写为可推翻条件。

## 3. 实验矩阵

每个场景都记录三条独立的轴，绝不合并成"查询是否相同"：

- **ack**：调用方观测到的应答类别
- **data**：重启后普通查询返回的行
- **history**：`/changes` 能追溯到的提交记录，以及 `history_base`

| ID | 场景 | 故障控制 | 关键问题 |
| --- | --- | --- | --- |
| S0 | `SIGKILL` after ack | 无（基线） | 已应答提交是否必然可见 |
| S1 | `SIGTERM` 两个窗口 | 真实停机 | 停机中的提交如何被应答 |
| S2 | 丢弃应答 + 盲重试 | 真实传输中断 | 无应答后重试的代价 |
| S3 | 进程内 `fsync` 失败 | ptrace `ENOSYS` | `error` 应答是否等于未发布 |
| S4 | 真实写入失败 | `RLIMIT_FSIZE` `EFBIG` | 半帧是否被拒绝重放 |
| S5 | 备份 → 再写 → 还原 | 无 | 还原副本是哪一刻的状态 |
| S6 | 目录复制 vs 校验还原 | 无 | 行相同是否等于历史相同 |
| S7 | 三类重开边界 | 文件级篡改 | 截断/损坏/坏图像的边界 |

所有场景在 `evidence/canonical-native.json` 中保留**每一轮**原始记录
（`trials`），不只保留第一轮。

## 4. 结果

### 4.1 稳定的一轮（15/15 轮签名一致）

以下数字取自 `canonical-native.json` 的 `scenarios`（首轮）与 `repetitions`
（15 轮分布）。

| ID | ack | data | history | 判定 |
| --- | --- | --- | --- | --- |
| S0 | `2xx` 200 | keys `[1,2,3]` | 提交 seq 2 | 配对成立 |
| S1-A | `2xx` 200 | keys 含 `11,12,13`，原子 | 提交 seq 3 | 配对成立 |
| S1-B | `no_response` | 未发布 `21` | 无 | 配对成立（拒绝） |
| S2 | `no_response` | keys `[7]` | **两条** `int:7` 提交 | **不配对** |
| S3 | `error` 503 | keys `[1,2,3,4]` | 提交 seq 3 存在 | **不配对** |
| S4 | `error` 503 | keys `[1]` | 无新提交，尾 40 B 被截断 | 配对成立 |
| S5 | — | 还原=备份点 | `history_base=2`，`after=0` 返回 410 | 见 4.3 |
| S6 | — | 行相同 | 副本 base=0 / 还原 base=2 | **不配对** |
| S7 | — | 见 4.4 | — | 配对成立 |

### 4.2 两个"最终查询相同但交付不等价"的反例

#### 反例一：`error` 应答之后数据仍然存在（S3）

```
ack:      503 unavailable "durable commit failed: sync ... function not implemented"
journal:  434 B -> 1032 B（写入已发生）
restart:  keys [1,2,3,4]，变更历史含 seq 3
injection_fired: true（15/15）
```

产品在 `fsync` 失败时拒绝发布并停止服务（这是正确的保守行为），但**帧字节已经
写进文件**。本次没有丢弃页缓存，所以重启后完整帧被正常重放。

若只看"重启后查询结果与一次正常提交相同"，会得出"等价"的错误结论。实际契约是：
**调用方收到 503，却无法据此推断数据不存在**。这正是 README 所说"调用方可能无法
确定该次提交最终是否落盘"的可复现形态。15/15 轮全部重现。

#### 反例二：行完全一致，变更历史不同（S6）

```
源库 head:      seq 2, history_base 0
目录复制:       rows [1,2]  history_base 0  /changes -> 200, 2 条提交
校验还原:       rows [1,2]  history_base 2  /changes -> 410
```

两者 `rows_match_point` 均为 true（行相同），但变更消费者看到的历史完全不同：
目录复制保留了原始两条提交记录，还原副本在新基点之前返回 410。**用行相等判定
两者等价，会让下游消费者重复或丢失提交。**

### 4.3 备份还原的确认边界（S5）

- 备份时 head=`seq 2`；备份之后源库又提交了 `seq 3`。
- 还原后：`data_restored_equals_backup_point=true`，
  `data_restored_equals_source_head=false`。
- `history_base` 从 0 变为 2；`GET /changes?after=0` 返回 **410**
  （`change history begins at 2`）。
- 游标探测：`after=1` → 410；`after=2` → 200 空页；`after=3` → 400
  （超前游标拒绝）。
- 历史快照探测：`at=1` → 200 空；`at=2` → 200 keys `[1,2]`；`at=3` → 410。

即：**还原保留图像内的历史读版本，但不包含源库的变更日志**。变更消费者必须从
恢复基点重新对齐，旧游标一律 410——与产品规范一致，且可被上述游标探测直接观察。

### 4.4 重开边界（S7，15/15 一致）

| 情形 | 结果 |
| --- | --- |
| 尾部追加 3 个零字节 | 启动成功，`recovered_tail_bytes=3`，`[1,2]` 保留 |
| 完整帧末字节翻转 | **拒绝启动**，`journal checksum mismatch at 260` |
| 图像 payload 改写 | **拒绝安装**，`image format or digest mismatch`，**目标目录未创建** |

第三项同时验证了"校验先于安装"：`target_dir_created=false`，失败后没有残留半成品。

### 4.5 停机窗口（S1）

两个窗口产生**不同的应答类别**，且都自洽：

- 窗口 A（提交已在 handler 内）：`2xx`，`[11,12,13]` 全量原子发布。
- 窗口 B（关机后才发起）：`no_response`，`21` 未发布。首轮错误信息为
  `no transaction could be opened during shutdown`，即停机开始后无法再开事务。

窗口 B 的登记范围必须精确，否则会被误读：

- 在当前**双窗口**场景下，窗口 B 在 **35 轮（20 + 15）中全部为 `no_response`，
  从未发布 `21`**。这是确定性观测，不是偶发。
- 早期有一个**单窗口**版本的 S1（只提交一次、随即 SIGTERM），其 8 轮全部拿到
  `2xx` 并正常发布。那是"提交先于信号到达"的窗口，**不是**本节的窗口 B。
  该旧版本已被双窗口版本取代，不得与本结论混用。

因此本节能确定的结论是：**停机开始后新发起的提交会被拒绝；已在 handler 内的提交
会被完整应答并原子发布。** 窗口 B 被接受的分支在当前场景中**未观测到**，其存在性
与频率均未测量，故不作任何断言。

还有一点必须说明，否则会低估窗口 B 的复杂度：早期在 `PTRACE_O_EXITKILL` 未移除时，
S3 有 2/7 轮把 `error` 变成 `no_response`。那是注入器退出时连带杀掉被测进程造成的
**工具伪影**，不是产品行为。修复后 10/10 稳定。这条记录保留在案，因为它说明了
为什么故障控制必须先自证不污染观测（见 8.1）。

## 6. 可推翻结论的条件

本文结论不是"LaminaDB 不可靠"或"容器与原生等价"，而是若干**有条件的**判断。
下列任一条件成立，对应结论即被推翻，需要重做：

1. **若在能丢弃页缓存或使用块设备错误注入的环境中重跑 S3，且重启后数据不存在**
   → S3 的"数据存活"结论只适用于"介质未真正丢字节"的场景，必须改写为
   "应答与效果不配对，方向取决于介质是否丢字节"。（当前环境正是前者。）
2. **若 S4 的 `recovered_tail_bytes` 在某轮不是 40 或数据出现部分提交**
   → "半帧被可靠截断"不成立。
3. **若在窗口 B 中观测到 `2xx` 且 `21` 被发布** → S1 的结论应改为"窗口 B 也
   可能被接受"，当前"停机后新提交被拒绝"的表述即被推翻。当前双窗口场景 35/35
   未出现该分支，故该分支存在性未定。
4. **若容器实测中任一场景的观测类别与原生不同**（例如 503 变 200，或
   `no_response` 变 `2xx`）→ 容器列与原生列不可合并，必须分别陈述。
5. **若还原副本的 `/changes?after=0` 不再返回 410** → 备份还原的历史边界改变。
6. **若用修改过的二进制/镜像使两端结果"对齐"** → 本实验的对照失去意义，结论作废。
7. **若 S6 的 `rows_match_point` 为 false** → 该轮是 harness 错误而非发现，
   需按 `harness_error` 处理。

## 7. 已知限制

- **容器列未测量**（无运行时）。容器对耐久性的影响主要在存储栈（overlay upper、
  bind mount、named volume、网络卷），必须先测 `stat -f` 与 fsync 成本，再谈应答语义。
- **没有掉电语义**。`SIGKILL` 保留页缓存，因此所有"重启后仍在"的结论都弱于
  "fsync 后掉电仍在"。
- **fsync 注入是故障控制，不是介质模型**。它让真实错误路径被走到，但不丢字节。
- **S1 窗口 B 的稀有分支频率未测量**。
- 数据规模小（单场景 ≤ 1000 行、≤ 15 MB/帧），未覆盖容量上限附近的行为。
- `history` 轴只读 `/changes` 与 `history_base`，未验证消费者端去重协议（产品
  明确没有请求级去重）。

### 8.1 两个工具陷阱（已在代码中记录，避免下一位使用者重复踩坑）

1. **arm64 上 `x8` 不是内核分发的系统调用号。** 只改 `x8` 会让 `fsync` 静默成功，
   而工具却报告"已注入"——一个会自我欺骗的假成功。必须改写
   `NT_ARM_SYSTEM_CALL` 并读回校验。本工具的 `set_syscall_nr` 后立即 `get_syscall_nr`
   并在不一致时如实报错。
2. **`PTRACE_O_EXITKILL` 会在注入器退出时杀掉被测进程。** 早期版本因此把 2/7 轮
   的 `error` 变成了 `no_response`，看起来像产品问题，实为工具伪影。移除后
   10/10 稳定。**故障注入工具必须先证明自己没有污染观测。**

## 9. 结论（按证据强度分级）

| 结论 | 强度 | 依据 |
| --- | --- | --- |
| 已应答的提交在非掉电重启后仍在 | 高（15/15，真实 SIGKILL） | S0 |
| `error` 应答不蕴含"数据不存在" | 高（15/15，真实 `ENOSYS` 路径） | S3 |
| 写入失败时半帧被截断且不重放 | 高（15/15，真实 `EFBIG`） | S4 |
| 无应答后盲重试会产生重复提交记录 | 高（15/15） | S2 |
| 还原副本是备份点，历史从新基点开始 | 高（15/15，游标与快照双重探测） | S5 |
| 行相同 ≠ 历史相同（复制 vs 还原） | 高（15/15） | S6 |
| 完整损坏/坏图像被拒绝且不落盘 | 高（15/15） | S7 |
| 停机窗口决定应答类别 | 高（两窗口各 35 轮一致） | S1 |
| 容器环境与原生等价 | **无证据（未测量）** | — |

**交付判定：** 本次可断言"原生环境下三种确认结果与其效果是否配对，已在上述
八个场景中被确定性观测"；**不可断言**"容器与原生耐久性等价"，也**不可断言**
"掉电后仍等价"。后两者需要第 6 节列出的额外环境与条件。
